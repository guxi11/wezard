# 金字塔 + 需求即工单 —— 组织结构设计 (方案, 未落地)

前置: `.ownermode` 的「责任树 + 四类非责任边」(turn tf383f5)。本方案保留它的核心不变量 —— **每件活只有一个负责人, 回执父 k 是严格的树** —— 但不再把依赖 / 评审 / 借调 / 上下文来源单独做成图, 而是把它们都挂进**工单树**里作为节点和成员的属性。

## 0. 一句话

**金字塔的节点是工单, 不是 wizard。** 每张工单 = 一层的管辖范围: 一个负责人 (owner, 这一层的 lead) + 它的直接下属 (members)。工单之间用 `parent` 连成树, 这棵树就是金字塔。一个 wizard 在不同工单里可以有不同角色, 但在任意一张工单里只有一个上级。

为什么挂在工单上而不是 wizard 上: wizard 是长住的、跨需求的 (一个 rolepage 专家今天给 R12 干活, 明天给 R15 干活); 责任关系却是**按需求**成立、按需求解散的。把树建在 wizard 上, 借调和复用都会撕裂它; 建在工单上, 树随需求生灭, wizard 只是在里面「任职」。

## 1. 层级定义

| 层 | 角色 | 谁 | 负责什么 | 对上说什么 | 对下说什么 |
|---|---|---|---|---|---|
| L0 | 甲方 | 人 | 提需求、在闸口拍板、验收 | — | 需求原话; 闸口上的「行 / 不行 / 改成…」 |
| L1 | 管家 (顶层) | 群的默认 wizard | 收需求、判断是新需求还是旧需求的续篇、写验收标准、开**需求根工单**、指定 L2、在闸口问人、交付时向人解释 | 对人: 结论、取舍、要拍板的, 不讲过程 | 对 L2: 需求 + 验收标准 + 约束 |
| L2 | 需求 lead | `dispatch({lead:true})` 起的 hard 档 | 想清楚、拆活、派活、组织评审、build/验证/提交、对整件需求的结果负责 | 对 L1: `RESULT` (做成了什么 · commit · 遗留) / `NEED` (要人拍板的) + 证据指针 | 对 L3: 一段活 + 验收标准 |
| L2′ | 子 lead (可选) | 同上, 由 L2 起 | 只在一块子活自己也需要「拆 + 审」时才出现 | 同 L2, 对 L2 | 同 L2 |
| L3 | 执行 / 评审 / 专家 | coder (clone 或 spawn)、白板 reviewer、借来的长住专家 | 只干分到的那一段 | `RESULT` / `NEED` / `VERDICT` | — |

**弹性层数**: 层只在管辖面需要时才长出来。一句话的小活, 管家直接派给一个执行者 (根工单只有一个成员, 管家兼 lead); 要 coder + reviewer 的才有 L2; L2′ 很少见。深度上限 4 (L0–L3, 含 L2′ 时 L3 在第 5 层, 不再往下)。

**说话的规矩 (守护进程能拦的标 ⛔, 只靠宪章的标 ✎)**:
- 只和相邻层说话。⛔ 带 `job` 的 `task` 只能由该工单的 owner 发给该工单的成员。
- 同一张工单里的成员之间只许 `ask` / `fyi` (问一句、知会一句), 不许横向派 `task` ⛔; 跨工单横向一律不许, 只能 `read_chat` / `peek_peer` 只读 ✎。
- 上层不越级给下层派活 ⛔ (越级只读不写: 管家可以 peek coder, 但打回只能通过 lead)。
- 人只和 L1 说话 (顶层模式, 已落地) —— 顶层模式就是这套规矩在 L0/L1 边界上的特例。
- NEED 逐层上冒: 每一层先自己答, 答不了才再往上 `NEED`; 到 L1 的需要人拍板的进管家的挂起事项表。

**对上隐藏实现, 不隐藏状态**: 上层看不到下层的往返, 但工单账本 (谁在干、卡在哪、几份落定) 对整条祖先链透明, 不用问、不用转述。rolepage 上人可以一路钻到底。

## 2. 四类「图边」怎么放进树里

| 原来的边 | 放进工单树后 |
|---|---|
| 依赖 `after` | 同一张工单里**兄弟成员**之间的顺序: 成员 B 的那段活 `after: [A]`。守护进程等 A 落定 `done` 再投 B, 并把 A 的 RESULT / ARTIFACT 附进 B 的信封。B 的回执仍回 owner (不改 k)。子工单之间同理。 |
| 评审 `review` + quorum | 工单的**验收闸**: 工单属性 `accept: "review", quorum: n`; reviewer 是这张工单里角色为 `reviewer` 的成员。`VERDICT: fail` 由守护进程以 owner 的名义 `re` 打回作者; 法定数没到, owner 的 `close_job` 被拒。 |
| 借调 `lease` | 成员角色 `expert`, `spawned:false`, 记「借自哪里」; 收工归还 (不回收)。它在这张工单里只答 `ask`, 不领 `task` —— 领 task 就是正式成员, 同时只能在一张工单里当执行者。 |
| 上下文来源 `forkOf` | 成员属性「材料来自 .x」(clone 时自动记)。用途: lead 要再派一段同材料的活, 账本直接告诉它该从谁 clone。 |

这样没有第二张图: 依赖是兄弟间的顺序, 评审是节点的闸, 借调与 forkOf 是成员的属性。关系图 (rolepage) 按工单树画, 边的类型只是节点 / 成员上的徽标。

## 3. 需求即工单: 生命周期

### 3.1 什么算需求
管家**派出去的每一件事**都是一张根工单 (`dispatch` 自动开); 管家自己一两句答完的问话不是。工单只是账本, 不占 pane, 所以「小活也开单」几乎没有成本, 换来的是每件事都有编号、有状态、有归档。

### 3.2 状态 (尽量现算, 不落盘)

```
收单 ──▶ 澄清 ──[G1]──▶ 规划 ──[G2?]──▶ 实施 ⇄ 评审 ──▶ 交付 ──[G3]──▶ 归档
  │        │                      │          │                 │
  └────────┴──────── 搁置 / 取消 ◀┴──────────┴───── 返工 ◀─────┘
```

| 状态 | 怎么判定 (现算) | 谁在推 |
|---|---|---|
| 收单 | 根工单刚开, 还没写验收标准 | 管家 |
| 澄清 | 管家向人 `NEED` 了, 挂起事项表里有它 | 管家 → 人 |
| 规划 | 已指定 lead, lead 的子工单还没有成员 | lead |
| 实施 | 子工单有成员在 working / blocked / needs-input | lead |
| 评审 | 实施件都 done, reviewer 成员在跑或法定数未到 | lead + reviewer |
| 交付 | lead 已 `close_job`, 根工单的那一份 done, 管家已向人交代 | 管家 → 人 |
| 归档 | 人认可 (或超时默认认可), 管家关根工单, 收工结论进 episodes | 管家 |
| 搁置 / 取消 | 人说先放着 / 不要了; 搁置保留账本, 取消回收全部分身 | 管家 |

只有三样要落盘: 验收标准、闸口是否已过、是否搁置 / 归档。其余都从账本 + 回执槽 + pane 探针现算, 跟 `turn-state.ts` 的「在飞活状态」同一个思路 —— reload 不需要恢复状态机。

### 3.3 人在哪拍板 (闸口)

- **G1 需求确认** —— 只在管家**猜了**验收标准、或需求要走 lead 时才问; 管家用一句话复述「我理解要做 X, 做成的标准是 Y」, 人回「对」或改。说得够清楚的小活直接派, 不打扰人。
- **G2 方案确认** —— 只在 lead 判断有不可逆 / 架构级取舍时: lead 以 `NEED: 方案 …` 收口, 管家转述给人。默认不设。
- **G3 交付验收** —— 管家交代完结果, 工单停在「交付」。人下一句话若是在说它: 「好」→ 归档; 「这里不对」→ 管家 `re` 给 lead 返工 (同一张单, 不开新单)。人一直不理: 见 NEED ④。

### 3.4 管家在哪介入
收单 (新单还是续篇)、写验收标准、选 lead、每个闸口、长时间不动的单 (deadline 过了自己 `peek` 一眼, 必要时 `notify` 一句进展)、交付解释、归档。**实施和评审期间管家不插手**, 只看账本。

### 3.5 和现有机制的关系

- **parent (家谱)**: 为工单生出来的分身, parent = 该工单的 owner。家谱树 ≈ 工单树在 wizard 上的投影, 但以工单为准 (借来的专家家谱不变)。
- **lead**: 「是不是 lead」从 wizard 的布尔属性变成工单关系: 一个 wizard 是某张工单的 owner, 它在那张单里就是 lead。`wizard.lead` 只留着决定出生宪章要不要带组队打法。
- **回执链**: 回执父 k 是「这一轮」的调用树, 工单树是「这件需求」的持久责任树。不变量: 带 `job: J` 的 task 一定由 owner(J) 发给 J 的成员, 所以每条 k 边都落在某条工单边上。闸口会把一条 k 链切断 (人可能隔天才回), 断开后靠工单号续上 —— 管家 `re` 到 lead, 新链挂回同一张单。
- **rolepage**: 已有的工单页 `j:<id>` 加上: 面包屑 (往上到根)、子工单列表、状态时间线、闸口记录、每个成员的角色 (执行 / 评审 / 专家 / 材料来自)。关系图按根工单分组。
- **挂起事项表 (pending_items)**: 管家的待办里多一类「等人过闸 / 等人验收」的单。

## 5. 风险与取舍

| 风险 | 对策 |
|---|---|
| **lead 瓶颈** (所有回执都串行过它) | ① 管辖面上限: 一张单的直接成员 ≤ 5 (现在是 12, 那是 fd 刹车不是管理幅度), 超了就长一层子 lead; ② `after` 让 lead 一次派完, 守护进程按就绪顺序放; ③ 评审 fail 由守护进程自动打回, 不经 lead 转述; ④ 成员间允许 `ask`, 小问题不绕 lead; ⑤ lead 不写实现。 |
| **逐层压缩丢信息** | ① 结论走 RESULT, 证据走路径: 每层的 RESULT 必须带 commit / ARTIFACT 指针, 上层要细节就按指针读原件, 不让中层转述 (工单黑板, `.ownermode` 第 5 步); ② 账本给每个成员存一份 RESULT 摘要, 祖先链都能读; ③ 取舍类信息最容易被压掉 —— 要求 lead 的 RESULT 单列「取舍 / 遗留」一段, 管家对人交代时必须带上。 |
| **层太多, 成本翻倍** (每层一个 hard 档) | 弹性层数 (§1): 只有在需要拆 + 审时才有 lead; 一句话的活不过 L2。管家给 lead 的派活带 `deadline` 和 `maxTurns`。 |
| **宪章膨胀** | 出生宪章只留「我在哪一层」三五行; 角色打法随派活信封带 (同 `renderLead` 现在对已有 wizard 的做法); 机制写在工具描述里。第 3 步要量一次 charter token, 不得高于现在。 |
| **工单粒度争议** (续篇 vs 新单) | 规矩: 同一份验收标准内的改动 = 同一张单 (返工 / 补丁), 新的验收标准 = 新单 (可记 `relates`)。管家判断, 挂起表的「可能在答哪件」提示兜底。 |
| **人不回闸口, 单子堆积** | 挂起表 + 管家每天一次汇总 (可做成定时任务, 带 gate 没单就不打扰)。见 NEED ④。 |
| **reload** | 工单是账本 (落盘), 依赖停放与评审法定数落在回执槽 / 账本里, 控制流仍在 wizard 上下文里 —— 与现在同一个取舍: 重启后重试一次接上, 不复活状态机。 |
| **借来的专家在多张单里被抢** | 专家在别的单里只答 `ask`, 不领 `task`; 领 task 要先从原单释放。 |
| **横向 `ask` 被写成变相派活** | 守护进程只能拦 `kind`; 账本给 owner 记一笔「谁问了谁」, 由 lead 看见兜底 (同 `.ownermode` 的判断)。 |
| **管家上下文膨胀** | 管家手里只有单号表, 详情在账本; 它可以随时 handoff, 新会话从挂起表 + list_jobs 读回现场。 |

## 6. 要人拍板 (NEED)

1. **闸口默认值**: 建议 G1 只在管家猜了验收标准或走 lead 时问、G2 默认不设 (lead 觉得有不可逆取舍才提)、G3 交付后等人一句话。还是希望每张单都显式确认需求?
2. **小活也开单?** 建议管家派出去的每件都开根单 (只是账本, 无成本); 还是只有走 lead 的才算「需求」?
3. **管辖面与深度**: 每张单直接成员 ≤ 5、总深度到 L3 (含 L2′ 最多再深一层) 是否合适?
4. **人不验收怎么办**: 交付后 N 天没人理 → 自动归档 (建议 3 天, 归档前管家提醒一次), 还是一直开着?
5. **单号进群**: 管家对人的回复里带短单号 (`R12`), 人可以用「R12 …」直接续一件事。可以接受这点「噪音」吗?
