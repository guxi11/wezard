# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

`wezard` (CLI `wezard`) bridges agent CLIs (Claude Code / claude-internal / CodeBuddy) and WeCom (企业微信) smart bots:
- **PreToolUse approval forwarding**: every tool call is gated by a button card pushed to WeCom; clicking ✅/❌/⏱ resolves the long-poll the hook is parked on.
- **Remote control**: messages sent to the bot drive a local agent CLI — the daemon spawns an interactive session in tmux and mirrors it to the chat. Sessions are opened from the chat side (first inbound, `/new`, `.name`, `switch_claude_session`) or by a wizard (`spawn_wizard` / `clone_wizard` / `delegate`).
- **MCP server** (`wezard`): the wizard's whole tool surface, each tool one thin POST to the resident daemon over loopback HTTP — rooms (`chat_ask` / `chat_reply` / `chat_say` / `room_*`: the only way wizards talk), delegation (`delegate`, `route_candidates`), spawn / clone / stop (`spawn_wizard`, `clone_wizard`, `stop_wizard`), awareness (`wizard_roster`, `peek_peer`, `pending_items`, `wizard_whoami`), identity and memory (`wizard_identity`, `wizard_remember`), owner-managed plans (`plan_*`), schedules (`schedule_task` / `list_tasks` / `cancel_task`), `handoff`, workspace/model switching, `notify` / `send_file`, config (`config_get` / `config_set`). Human-facing outbound cards (approval / AskUserQuestion) are pushed by the daemon itself, not through MCP.

## Build / run

```bash
npm run build        # tsc → dist/, then chmod +x on the bin entry scripts
npm run typecheck    # tsc --noEmit
npm run dev:daemon   # tsx daemon/index.ts  (no install / hot iteration)
npm run dev:cli      # tsx cli/init.ts
```

Tests are individual assertion scripts under `tests/`; there is no `npm test` script. Run relevant TypeScript scripts with `npx tsx tests/<name>.test.ts` after checking prerequisites. Typechecking excludes tests. Documentation changes require link and command review.

Local dev loop:
```bash
npm run build && ./cli/wezard.sh reload    # rebuild, then bounce the resident daemon
./cli/wezard.sh logs -f                    # tail ~/.wezard/daemon.log
./cli/wezard.sh status                     # HTTP /status — wsConnected, pending count, sourcePath
```

When the user says **"reload"** in this repo, it means exactly: `npm run build && ./cli/wezard.sh reload`. The global `wezard` binary may not be on `$PATH` in dev shells — always invoke `./cli/wezard.sh` from the repo root. After a development unit, build once, reload the daemon, then restart the existing svr service with `launchctl kickstart -k "gui/$(id -u)/com.wezard.svr"` on macOS or `systemctl --user restart wezard-svr.service` on Linux. Operational-only requests keep their requested scope; daemon reload does not restart svr.

## High-level architecture

Three processes, all coordinating via 127.0.0.1:17890 and `~/.wezard/`:

```
 WeCom  ── WS ──►  daemon (resident, launchd/systemd --user)
                     │
                     ├── HTTP :17890 ───────► hook (pre-tool-use.sh, blocking long-poll)
                     ├── HTTP :17890 ───────► MCP server (stdio child of claude)
                     └── tmux pane running the agent CLI ── mirror bridge (tail jsonl + tmux paste)
```

**daemon** (`daemon/`) is the only process that holds the WeCom WSClient. Everything else is a thin HTTP client of it.
- `index.ts` wires modules; route handlers are registered onto the http server returned by `startHttp`.
- `ws.ts` owns the `@wecom/aibot-node-sdk` `WSClient`. Fatal auth/reconnect → `process.exit(1)` (launchd respawns).
- `approval.ts` builds the button card, parks an HTTP request via `pending.ts`, and resolves it on `event.template_card_event`. Three click outcomes: `allow` / `allow_window` (auto-allow N min for that session) / `deny`. `session-cache.ts` short-circuits repeats.
- `inbound.ts` routes `message.text` / `message.image` / `message.mixed` → `mirror-bridge.ts`. Gates on `allowFrom`; one-shot exception is the bootstrap claim (see below).
- `mirror-bridge.ts` tails `<projectsDir>/<encoded(cwd)>/<sid>.jsonl` and records every turn into the turn store (the rolepage's "how it was done"). **It delivers a turn's final text to no one** (`concludeBriefTurn`: final lines have zero routing semantics): a wizard speaks into a chat only through room tools (`chat_say` / `chat_reply` / `notify`), which the room hub mirrors out. What mirror still pushes to the chat itself: approval/askq cards, `[mirror]` notices, and the placeholder "brief" bubble opened when a human line arrives (the first `re`ing reply covers it; `hardTimer` closes it before WeCom's ~6 min stream window). Inbound injection is either `claude --resume <sid> -p` (writes a turn into the same jsonl) or `tmux paste-buffer` against a live TTY (only path that makes WeCom messages visible in the user's CLI window). `recentInjects` ring buffer suppresses the WeCom→CLI echo when tailing (which is why an injected line's text is stamped as the turn's `userQuery` at inject time — the tail never sees it). **Every turn has a channel** (`TurnDetailRecord.channel`): the chat it was spoken in (`""` = a private wizard↔wizard turn); the rolepage files the turn by it, and follow-up injections that serve the turn (approval resumes, handoff carry) inherit it.
- `claim.ts` is a single-shot bootstrap: an exact-match magic phrase from any sender bypasses `allowFrom`, writes that principal as `defaultChat`, and appends to `allowFrom`. This is the **only** legitimate ingress for first-time setup.
- `peers.ts` is the read side of multi-agent awareness — "who else is working in this chat, and are they busy". A wizard's HOME chat is its target key's base principal (`baseOfKey`): the untagged default plus every slot `chat:xxx#slot`. Pure parsing only — bounded transcript-tail reads (`talkTurns` / `lastAssistantText` / `summarizeTail`, the last shared with `session-scan.ts`) and pane classification (`paneIsBusy`). **What a wizard reads about another comes from the transcript, never from a pane capture**: text turns only (`talkTurns`), and "where is it stuck" is `openToolUses` (a tool call left hanging on an idle session = parked on an approval card). The pane is consulted for exactly one thing, `busy`. Read-side tools (`wizard_roster` / `peek_peer` / `room_read`) answer in plain text rendered daemon-side, not json; `room_read` renders a room's ledger (`shared/room-view.ts`), not a transcript. Which channel a line belongs to and who said it is read back from the envelope riding on that user line (`parseEnvelope`, `shared/reminder.ts`): every wezard `<system-reminder>` carries its facts as opening-tag attributes (`wezard=envelope|hint|lead|after|mention|roster|pending`, `kind` / `from` / `chat` / `scope`, the injection event id as `msg`) and its prose only for the model; which attrs each kind may write is the `REMINDER_KINDS` registry (each attr is either read back by code or an id the model copies into `re`/`for`/`drop`), and `renderTail` lays one injection's tail out in a fixed order, envelope first — rewording the prose never breaks parsing; only the current attribute envelope is parsed, without inferring facts from older prose. The rolepage collapses each reminder into a tag named by its kind (`<envelope · .x>`, `<回执 · .x · need>`, `<roster>` …) that expands to raw on click; no envelope = a human speaking in the session's home chat. A clone's transcript starts with its parent's forked history, so its rounds older than `bornAt` are dropped. Identity (name / responsibility / memory / lineage) lives in `wizard.ts`, not here. **Busy detection matches the TUI spinner footer** (`… (12m 31s · …)` on current versions, `esc to interrupt` on older ones) in the last 8 non-blank rows — transcript mtime is useless here, it goes quiet during long tool calls.
- `wizard.ts` is the identity layer over those sessions: a target key plus a **globally unique name** — the wizard's only address, written `.name` everywhere a human or model sees it (a chat's default session takes the chat's name, a slot takes its slot id; collisions get `-N` via `pickName`; `settleName` claims lazily, `settleAll` initializes unnamed current identities at boot, default sessions first). The slot id inside the key is NOT the name: a rename never rekeys a session. Plus a one-line responsibility, a long-term `memory` list, and a `parent` link for management ownership. Every collaborative spawn/clone belongs to its caller, including cross-cwd/chat creation and cloning context from another wizard; `forkOf` records a different context source. Horizontal communication does not change parent ownership. Ending an identity is limited to itself or its direct parent; active/paused plans prevent logical retirement, and children must be handled before their parent can be forgotten. Completed work retains wizard identities by default; pane resource eviction keeps identity and binding. The registry is a write-through json (`~/.wezard/wizards.json`, `wrc.mirror.wizardsFile`) bound process-wide via `bindWizardStore` so the IM side can read it too; everything else in the module is a pure renderer. **Identity travels as the first message's preamble, not the system prompt**: `renderCharter` builds the wizard's charter (who it is, its workspace, its clones, its memory, the chat's and the workspace's shared memory (`wizard-memory.ts`: `~/.wezard/memory/{chats,workspaces}/*.md`, human-editable, appended by `wizard_remember({scope})`), the tool roster, the orchestration playbook, how to talk through rooms). `spawn-tmux` only parks it at `charters/<sid>.md` (claude/codebuddy no longer get `--append-system-prompt` — it cost ~1.4s per cold start); the attachment's `charterPending` prepends it as `<system-reminder wezard="charter">` to the pane's first non-slash injection and clears it once that injection is confirmed. It is re-armed on every moment a session has not read it: `/new`, a spare-pool claim, a dead-pane respawn, `/clear` and compaction (`onContextCut` → `armCharter`); a clone's opening line carries the child's charter, superseding the parent's inherited one. Read sides (`stripMeta`, `cleanUserText`, rolepage) strip/collapse the `charter` reminder, so it never becomes a chat ask or a bubble. Codex keeps it in `developer_instructions`. Every spawn path (`/new`, a dead-pane respawn, a clone) pulls it from `MirrorBridge.setCharterProvider`, installed in `index.ts`. Since a running wizard never sees a new charter, `config_set` renders every chartered wizard's charter before and after the change and tells the affected ones (and the caller) to `handoff` — generic over whatever config the charter reads. Backends with no such flag spawn without a charter rather than with a rejected flag.
- **Cloning is a context fork**: `MirrorBridge.cloneSession` spawns `--resume <parent sid> --fork-session`, so the child starts holding everything the parent had read while the parent is untouched — that is what makes "load the shared material once, then fan out" work. Two invariants: `--fork-session` is mandatory (without it a second pane appends to the parent's jsonl and two chats cross-wire), and the attach waits for the forked transcript (codebuddy 2.167 writes it at process start — a byte copy of the parent plus a `session-meta` row, no API call; older CLIs only on the first message); if it never appears the pane is killed rather than bound to the parent's sid.
- **Rooms are the only thing wizards talk through** (`shared/room.ts` pure core — row types, fold, `judge`, wake rules, ids; `daemon/rooms.ts` store; `daemon/room-hub.ts` the only append door + wake pump; contract in `docs/room/contract.md`). A WeCom group / DM / channel post is a *bound* room (id = the base principal verbatim); two wizards' conversation is an unbound `dm:<uidA>|<uidB>` room (stable instance uids, never names); 3+ is an `adhoc:<hex>` room opened with `room_open`. A room is one append-only, fsync-per-append jsonl under `<stateDir>/rooms/` (`roomsDirOf` is the single derivation — never `join(…, "rooms")` locally); state is a fold of the rows, a torn tail line is dropped, a corrupt middle line makes that room fail closed (503). Humans (inbound) and wizards (tools) append through the same `judge` (membership, who may write a `status`, dedup, wake targets, budget); a rejected line never becomes a row. **Completion, origin and the right to speak are explicit fields on ledger rows, never inferred from a transcript or a final line**: `chat_ask` opens a *duty* on its `to`; only that holder's `chat_reply` with status `done` / `passed` / `canceled` closes it (`need` / `progress` / `error` don't); `chat_say` / `notify` open nothing. `wakeTargets`: the named, the asker of a `re`, the host for an unaddressed human line in a bound room, and `room_watch` subscribers on human lines / closing replies; host = the earliest-joined wizard member, evaluated on read. A bound room mirrors every `msg` row to WeCom except `origin` inbound/migrate and `trigger` rows (`mirrors()`); dm/adhoc rows live only on the rolepage.
- **The wake pump keeps no queue** (`room-hub.ts`): who is owed what, and what to show them, is recomputed from the ledger every pass — a row with `wake∋uid` past the member's `seen` cursor is pending. The `seen` row is written only after a confirmed paste; an uncertain paste leaves the cursor and re-delivers the same batch marked "maybe already read", so a reload loses nothing. A target with no session at all (`gone`: its binding was dropped by `stop_wizard` end / `/kill`) is not woken by retrying: each duty it holds in the batch gets one `undelivered` system row to its asker (cursor untouched, so a same-name respawn still reads them); other failures log one warn per state change. A busy live pane waits for its turn to end; `interrupt:true` (direct parent / host / human only, budgeted per room) presses Esc first; a cold wizard is not "busy" — pasting respawns it. A wizard that ends a turn still owing a duty gets one reminder (in-turn via the Stop hook `hooks/stop.sh` for backends that honor `decision:block`, else at turn end), then a system row to the asker. `room-watchdog.ts` writes `canceled` for the duties of a wizard whose pane is truly gone (two confirming scans, never on a failed tmux call). `after` on a `chat_ask` defers the wake until the listed duties are `done`.
- **`delegate` / `route_candidates`** (`daemon/route.ts`, the deterministic half of dispatch): candidates are filtered and ordered by evidence (files it read > responsibility > recent asks; same workspace only breaks ties), each with its cost line (cache cold / ctx size → what waking it costs vs. a white-board spawn); `decide` takes the first candidate no veto rejects (weak evidence, busy, not worth it, cold cache with big ctx — `force` crosses only the last) or spawns a white-board wizard at `tierFor`. The product of `delegate` is one `chat_ask`; the caller may override (`to`, `spawn`, `force`, `tier`, `lead`). In-flight work is the room ledger's open duties (`openDuties` / `dutyFacts` in `shared/room-view.ts`); `shared/turn-state.ts`'s `TurnState` vocabulary survives only as a type — `WorldFacts.inflight` is always `[]`.
- **Steward hand-brake** (`approval.ts` / `steward-guard.ts`): triggered by role (`isStewardTarget`: the chat's bound steward, else its default session), ahead of every approval path — it may not edit files or open subagents, and caps its own look-commands per turn at `chatPolicy.<chat>.stewardBudget` (reading code — Read/Grep/Glob and read-only shell commands — passes free; the deny reason points at `delegate`). A new group's onboarding guide has no tool surface at all (`onboarding.ts` `guideRefusal`) except `chat_reply` / `chat_say` / `onboard_bind`.
- **Teams plans** (`shared/plan.ts`, `daemon/plans.ts`, `daemon/plan-http.ts`, `daemon/plan-reminders.ts`): each wizard may own multiple mutable DAG plans. `plan_create/get/list/update` expose explicit owner-managed state; only the owner writes, and `revision` is a compare-and-swap guard. Replacing `tasks` replaces the whole DAG. The store validates dependencies, task/plan states and terminal plans, uses owner-scoped `requestId` creation idempotency, and fsyncs an append-only `wrc.mirror.plansFile` journal (`~/.wezard/plans.jsonl` by default) before publishing changes in memory. Corrupt history or failed IO makes plan operations and retirement checks fail closed with 503 while receiver messaging remains available. The daemon never assigns executors, dispatches ready nodes, accepts plan task completion or advances plan state automatically; the owner thinks, delegates, reviews and updates explicitly. Clear, low-risk coding goes to light; independent reviewers start blank and use a tier appropriate to the review risk.
- **Plan association and reminders**: `chat_ask` / `delegate` take an optional `planId`, stored on the duty row as a record only — the daemon never advances the DAG. A plan's reminder is suppressed while its owner still holds an open duty with that `planId` (`planHasOutstandingDebt` reads the ledger); active plans are reminded only while the owner is idle and not handing off, paused plans stop reminding. A reminder is a `trigger` row (not mirrored, wakes only the owner), deduped by the persisted plan/revision/token marker, which does not bump `revision`; enqueue revalidates plan state / revision / token / debt / idle / handoff right before delivery.
- `notices.ts` is the other half of awareness. A charter's roster is a spawn-time snapshot and only gets staler; a variation (a birth, a `stop_wizard`, a changed job description, a chat getting named) posts one line into each affected wizard's in-memory box, and the next text injected into that pane — from a human, a peer or a scheduled task — carries it along as a `<system-reminder>`. No extra turn, no bubble, no transcript. Delivery clears the box: a notice is a hint, the truth is always `wizard_roster`.
- `chat-name.ts` turns a chat's unreadable `chat:wr…` id into a readable name (which its default wizard inherits), and auto-fills one from the workspace basename when nobody named it. The fill happens wherever a name is about to be handed to a model — including `renderCharter`, since a system prompt outlives the process that read it. Fill-only; a human-chosen name is never overwritten.
- `tasks.ts` fires a scheduled prompt into a target wizard's session — exactly equivalent to someone saying it in the chat at that moment. Lives in the daemon, not in a session, so a CLI restart / `/clear` / session end can't carry it away. It runs one fixed skeleton per shot — `trigger → gate → render → dispatch` — and nothing else: the *specifics* of each stage live in the task's own file, because a schedule is "run this logic at this time" and logic does not fit in json.
  - A task is `~/.wezard/tasks/<id>.task.mjs`, an ES module exporting `when` / `gate` / `prompt` / `target`+`fresh` / `owner` (the wizard that scheduled it — its rolepage shows the task under 日程) — **the config is source the wizard edits directly** (hot-reloaded by mtime; a file that fails to load keeps its previous version running and surfaces the reason in `list_tasks`). Source stays source: `lastFired` and the gate's cross-round memo live in `~/.wezard/task-state.json`, so the daemon never writes back over a file a wizard just edited.
  - `shared/trigger.ts` is the trigger AST (Specification + Interpreter). **Clock vs Guard is the whole point**: `every`/`daily`/`at` produce instants and answer "when next", `between`/`onDays`/`not` only veto. `and(clock, …guards)` is their intersection — that's what makes "白天每小时" expressible, and why `nextFire` enumerates clock candidates and picks the first one every guard passes. An AST, not a closure, because it must be renderable (`每 1 小时 · 08:00-21:00`), storable and drawable. `shared/schedule-spec.ts` under it is pure lexer (weekday / time-of-day / interval / window) — it grows with how people speak, the AST grows with how things are computed.
  - `gate` (`task-gate.ts`) runs **in a child process with a timeout**: it is user/wizard-written code that shells out, and a wedged gate must not stall every other schedule — timeout, throw and crash are all the same verdict, *hold fire this round*. Returning `false` costs nothing and says nothing; that is how "only if there's work" stops spending a pane per empty round. A gate **error** posts one bubble (only on the good→bad transition) — a broken gate's silence is indistinguishable from "nothing to do today".
- **rolepage** (`shared/chat-http.ts` routes, shared verbatim by the daemon and the standalone svr; `shared/room-view.ts` ledger read model, `shared/role-view.ts` / `role-render.ts` turn folding; frontend `web/chat.js`): `GET /role?id=<ticket>&role=<name|target|human:x>` is the SPA shell; data comes from `/api/world` (rooms + wizard/human nodes + genealogy + plans/schedules), `/api/room` (snapshot + history paging), `/api/wizard` (card + "its own + addressed to it" / all messages), `/api/turn` + `/api/tool` (a message's process box; tool bodies fetched on expand), `/api/charter`, `/api/search`. Two sources, neither replaces the other: the room ledger is *what was said* (author / completion / speak-right on the row), the turn store is *how it was done* (tool calls, CLI text, usage). A wizard page is turn-led — a turn folds into an in-message (the asker) and an out-message (the reply) — with ledger rows hung on the turn that produced them. `?id=` is an unguessable record id acting as the capability: any valid ticket may view every role. The standalone svr receives `WorldFacts` (`plans`, `rooms`, `names`, …) by POST; without a room reader it degrades to graph + members. The plan/schedule view is read-only; active/paused plan owners and their registered management ancestors stay visible. The sidebar and relationship cards share one conversation/window/unread implementation.
- **Retired** (no compatibility fallback): jobs, workflow runners and the graph executor with their MCP/HTTP entry points and `jobsFile`/`receiptsFile` configuration; the `daemon/router.ts` route ledger, receipts and `tell_peer` / `wait_peer` / `read_chat` / `send_peer` / `dispatch`; the `topOnly` / `speech` chat policy and public→private demotion (noise control is structural now: open a follow-up room, or pull people into the main one); `chatOriginOnly` / `slashAckFirstLine`. Old data is only read by the one-shot migration (`shared/room-migrate.ts`, `shared/legacy-routes.ts`, `cli/migrate-rooms.ts`). Generic idle waiting lives in `daemon/wait-idle.ts`.

**Configuration** (`shared/config.ts`):
- Loaded by every binary via `loadConfig()`. Resolution order: explicit arg → `$WEZARD_CONFIG` → `~/.wezard/config.jsonc` → `~/.wezard/config.json`.
- Secrets (`bot.botId`, `bot.secret`) live in `~/.wezard/secrets.json` and are deep-merged on top of the main config — keeps secrets out of dotfile repos.
- Schema is zod (`ConfigSchema`); shape mismatches throw with a path-pointed error.
- `shared/config-writer.ts` is the only sanctioned way to mutate the on-disk jsonc — it preserves comments via `jsonc-parser` edits. `cli/init.ts`, `daemon/claim.ts` and `daemon/chat-name.ts` use it.

**Shared primitives** — reach for these before writing a local copy:
- `shared/json-map-store.ts` (`loadJsonMap`) is the write-through keyed-JSON file behind recovery state such as `mirror-store.ts` and `wizard.ts`. Its tolerant reads/writes must not be reused for durable plan state: `daemon/plans.ts` owns the stricter fsync journal and health checks.
- `shared/exec-path.ts` (`augmentedPath`) — PATH widening for every daemon-side spawn.
- `shared/std.ts` — `sleep`, `truncate`, `truncateWithCount` (`…(+N)`), `clipLine` (collapse whitespace, then cut).
- `shared/paths.ts` (`expandHome`, `sanitizeId`), `shared/session-label.ts` (`tagOfKey` / `baseOfKey` / `withTagHeader` / `nameTokenRe` / `displayName` — use these names, don't re-alias them locally; names reach it through the injected `TagLinker`, since `shared/` can't import the daemon registry).

**Hook + sync**:
- **审批 hook 按会话注入, 不注册到全机**: `shared/session-hooks.ts` 写出 `<stateDir>/session-hooks.json` 和一个只带 hooks 的最小插件目录; spawn 时按其后端加 `--settings <file>` (claude / codebuddy) 或 `--plugin-dir <dir>` (claude-internal 1.x 没有 `--settings`)。同一个 pane 的启动行还带 `WEZARD_MANAGED=1` 与 daemon 地址 —— 它们原先由 sync 写进全机 settings 的 env, 现在只存在于 wezard 自己的进程里。codex 用 `shared/codex-hooks.ts` 的 `-c` 覆盖, 同理。
- **MCP 也按会话注入**: `shared/session-mcp.ts` 写出 `<stateDir>/session-mcp.json` (缺省传输 `daemon.mcpTransport:"http"` 时另写一份 `session-mcp-http.json`, 认 `type:"http"` 的 claude / claude-internal / codebuddy 用它, 名单外与 codex 回落 stdio), spawn 的启动行加 `--mcp-config <file>` (claude / claude-internal / codebuddy 都认, **不加 `--strict-mcp-config`** 否则会连用户自己的 MCP 一起挡掉)。`.claude-plugin/plugin.json` 不再声明 `mcpServers`, 仓库里也没有 `hooks/hooks.json` — 插件只提供 `commands/*`。
- `cli/sync.ts` 现在**只做清理**: 把老版本写进 `config.sync.targets` 各处的 wezard hook 条目 / `WEZARD_*` env / `mcpServers.wezard` (`~/.codebuddy/mcp.json` 与 `~/.claude-internal/settings.json` 两处) 删掉, 空壳对象一并删 — 重跑幂等, `--remove` 之后机器上不留 wezard 的任何注册。`~/.wezard/sync.lock.json` 只记录还剩哪些目标。 As a safety net the entry points (`hooks/pre-tool-use.sh`, `cli/codex-hook.ts`) still open with an ownership gate — only a CLI process wezard spawned carries `WEZARD_MANAGED=1` (launch line / headless inject env); anything else exits 0 with no output and stays on the CLI's own permission flow, never `allow`, never `ask`. Panes that predate the injection are covered by the `@wezard_managed` pane option the daemon stamps on every binding it attaches (one local `tmux show-options` in the hook, no daemon call). `~/.wezard/state/approval-mode` is the runtime override on top of that registration (`wezard use cli|wecom`): the file holds `cli` (absent = `wecom`), the hook reads it with a bare `cat` **before** it touches jq or the daemon and then exits 0 with no output — the CLI's own permission flow answers — while `daemon/approval.ts`, the picker sentinel and `cli/codex-hook.ts` treat the same file as "no cards, no auto-press". **A hook that cannot reach the daemon answers nothing, never `allow`**: silent auto-allow would hand a pane every permission while the human still believes approval is on. It waits only when the service is still registered (`launchctl print` / systemd `LoadState`), so `wezard stop` degrades to local CLI immediately instead of burning the 60s resume budget.

**MCP server** (`mcp/tools.ts` is the tool surface; `mcp/server.ts` is the stdio entry — its dist path is load-bearing, every pane config runs `node dist/mcp/server.js`; `daemon/mcp-http.ts` is the daemon's own stateless StreamableHTTP endpoint, the default transport, `daemon.mcpTransport`): stateless w.r.t. WeCom, every tool just `POST`s to the daemon. Add a tool in `mcp/tools.ts` AND a route handler in `daemon/`. Rarely used tools (`list_claude_sessions` / `switch_claude_session` / `list_chats`) register only with `WEZARD_MCP_EXTRA=1` — every registered tool costs model context. Collaboration tools (`wizard_whoami` / `wizard_identity` / `wizard_roster` / `spawn_wizard` / `clone_wizard` / `stop_wizard` / `wizard_remember` / `handoff` / `set_model` / `delegate` / `peek_peer`, the `chat_*` / `room_*` family, `plan_create/get/list/update`) all send `selfRef()` = `{sessionId, tmuxPane}` (stdio: env; http: per-request `mcpIdentity`) so the daemon can resolve *which* session is asking — env sessionId goes stale after a `/clear`, pane id doesn't. Discovery is layered: the charter (`renderCharter`) carries one "when to use" line per tool and is the only part guaranteed in context — Claude Code defers MCP tool schemas behind ToolSearch — while each tool description carries the mechanism and parameters. ## Important patterns / pitfalls

- **PATH for spawn**: anything the daemon spawns must go through `shared/exec-path.ts`'s `augmentedPath(process.env.PATH)` — launchd/systemd start it with a stripped PATH that often lacks nvm/homebrew, so a new spawn ENOENTs in production while working fine under `npm run dev:daemon`. Callers needing more dirs pass them as the second arg (`session-scan` adds `/usr/sbin` for `lsof`).
- **launchd respawn**: `KeepAlive.SuccessfulExit=false`. `wezard reload` does `POST /shutdown` AND `launchctl kickstart`; just hitting `/shutdown` won't bounce the binary.
- **Uninstall order**: `wezard uninstall` *before* `npm uninstall -g wezard`. Otherwise launchd repeatedly tries to relaunch a deleted binary. State at `~/.wezard/` is intentionally preserved.
- **Card update has a 5s window**: `client.updateTemplateCard` only works within 5s of the click event — `installApprovalEventListener` does the rewrite synchronously inside the event handler.
- **Transcripts** live under each backend's own projects root (`~/.claude/projects/`, `~/.claude-internal/projects/`, `~/.codebuddy/projects/`); `backendForPath` in `shared/cli-backends.ts` recovers the backend from a jsonl path.
- **Long-poll timeouts**: hook curl `--max-time` (`approval.hookTimeoutSec`, default 43210) must be **strictly larger** than `approval.longPollSec` (default 43200 = 12h), or the hook returns `ask` while the daemon is still waiting on a click.
- **Sensitive arg redaction** (`daemon/redact.ts`) runs before card render when `approval.sensitiveArgRedact=true`. Only the redacted form is shown in WeCom and stored in pending meta.
- **Daemon fd limit**: the launchd plist MUST set `SoftResourceLimits.NumberOfFiles` (template = 65536). The daemon restores one mirror per active session at boot (jsonl tail + subagent watchers + tmux spawn each), so a few hundred sessions exceed launchd's default 256 soft limit; `spawn` then throws `EBADF`, the process dies before `HTTP listening`, and `KeepAlive` wedges in a crash loop (`status` shows `down`, `launchctl` reports a stale pid). If `/status` is connection-refused while a launchd pid exists and `daemon.stderr.log` shows `spawn EBADF`, this is the cause — never "fix" it by editing the installed plist in `~/Library/LaunchAgents`, since `install.sh` regenerates it from `launchd/com.wezard.daemon.plist.template`; edit the template instead.

## Project conventions

`rules/chat.md` and `rules/code.md` (loaded from `~/develop/Guxi11/aiconfig/rules/`) take precedence over generic style. Highlights enforced in this codebase:
- Functional first: `map`/`filter`/`reduce`, deep-merge by recursion, immutable transforms; side effects pushed to module boundaries (file IO in `shared/`, child_process in bridges, network in `ws.ts` / `http.ts`).
- One function = one sentence. Helpers like `extractText`, `renderInput`, `decodeKey` are pure and testable in isolation; the IO-bearing functions wire them together.
- Comments in source files lean toward "why" (subtle invariants like the dual `event_key` path in `approval.ts`, the 5s update window, the dedup ring buffer). Preserve them on edits.
- Errors should never break the workflow: `approval.fallbackOnError` defaults to `ask`, a hook that can't reach the daemon answers nothing — the CLI's own permission flow decides, never `allow` (see Hook + sync); other hook failures emit `ask`, every WeCom send is wrapped in try/catch that logs and continues.


**Codex backend**: `shared/codex.ts` adapts response_item records and discovers date-partitioned rollouts using session_meta (cwd/id). `spawn-tmux.ts` prepares native threads through the installed Codex CLI's transient app-server (thread/start, resume or fork, then thread/name/set to persist without a turn), opens a tmux pane with codex resume, and binds the known id/path/pane immediately. SessionStart maintains identity after native session switches; never invent a Claude-style transcript path or send a bootstrap message. Long startup commands run through a private temporary script to avoid PTY input truncation. MCP and developer_instructions are invocation-local TOML overrides. `cli/codex-hook.ts` bridges PreToolUse and PermissionRequest to the shared IM approval engine. Native sandbox permissions always require their own card while approval is enabled; do not reuse tool windows/skip policies. Codex does not support PreToolUse ask: unavailable approval bridges deny ordinary tools, while PermissionRequest falls back to the native prompt. `wezard sync` owns only its exact handlers in Codex hooks.json and trust hashes in config.toml; preserve third-party hooks and never bypass all hook trust. Claude project config sync does not apply to Codex.
